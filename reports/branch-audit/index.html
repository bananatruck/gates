01

Executive verdict

The branch does not complete G.A.T.E.S.

!
Bottom line

Zura16’s branch should not be treated as a completed implementation or as valid empirical evidence. It replaces execution with caller-supplied dictionaries, replaces source coherence with hardcoded intervals, replaces report verification with regexes and a mock entailment rule, and then benchmarks those mechanisms using fixtures designed to produce the advertised outcome.

04

Implementation review

Gate-by-gate findings

Gate 1

Execution validity

Question: did this code run, and did this run produce these values?

Regressed

Required by the base design

  • Fresh child process and process-group timeout
  • Full, separate stdout and stderr capture
  • Child-computed code identity
  • Typed results with call-site provenance
  • Trace IDs and causal registry chain
  • Deterministic verdict plus grounded feedback

What Zura16 implements

  • Trusts a caller-provided execution_result
  • Defaults a missing exit code to success
  • Does not implement unbound-name analysis
  • Does not ban forged clean exits
  • Code-identity mismatch branch contains only pass
  • Accepts unbound code plus fabricated results_json
Base contract R3–R4Branch source R7
Gate 2

Source ↔ result coherence

Question: do measured results cohere with the cited method, dataset, setting, and claims?

Toy checker

Required by the base design

  • Gate 1’s verified value registry
  • Retrieved full-text literature corpus
  • Plan’s declared claims and settings
  • Principled prediction/tolerance intervals
  • Measured semantic-tier accuracy and confidence interval
  • Two-turn loop with declared limitation on exhaustion

What Zura16 implements

  • No source documents or plan claims enter the evaluator
  • Three hardcoded method/dataset ranges
  • Unknown methods silently skip source checks
  • Negative loss and speedup can pass
  • Fallback “LLM” is one SGC/Cora heuristic
  • OPTION_C lets a model directly fail the verdict
Base contract R2Branch source R8
Gate 3

Report validity

Question: does every manuscript number, citation, figure, and claim resolve to evidence?

Bypassable

Required by the base design

  • No raw result numerals in result contexts
  • Every result token resolves to a citable value
  • Rendered values match the registry exactly
  • Bibliography generated from fetched metadata
  • Figures exist and trace to gated runs
  • Measured model-assisted claim entailment

What Zura16 implements

  • Scans only decimal literals inside table blocks
  • One result token disables raw-number checks for the table
  • Rounds 0.815 to 0.81
  • Checks citation strings against a hardcoded set
  • Searches prose “Figure 1,” not \includegraphics
  • Empty paper and unsupported prose both pass at 1.0 entailment

Empirical evidence

The comparisons are fixtures, not experiments

10handwritten head-to-head tasks
3gated tasks that actually succeed
30%own committed citation-validity result

How the “head-to-head” is constructed

  1. Give the simulated baseline a hand-selected high reward.
  2. Preload its manuscript with wrong numbers or a fake citation.
  3. Supply the gated side a caller-asserted execution result.
  4. Label every successful gated pipeline as grounded.
  5. Set its fabrication rate to 0.0 directly.

What the committed artifacts reveal

  • Grounding is 100% only after conditioning on accepted cases.
  • Seven rejected gated cases disappear from that denominator.
  • Citation validity is 30%, contradicting the README’s 100% story.
  • Current source no longer reproduces some committed status names.
  • Repeated JSONL rows are reruns of identical fixtures, not independent samples.

What can be retained from Zura16’s branch

  • The high-level three-gate naming aligns with the plan.
  • Some tiny fixtures illustrate intended failure categories.
  • The report-token idea is directionally aligned with Gate 3.
  • The code can serve as disposable pseudocode—not evidence.

Minimum acceptance criteria for a replacement

  • Branch from current main and preserve its tests.
  • Use the verified Gate 1 registry, never caller-supplied numbers.
  • Wire real AgentLaboratory phases and actual agent revisions.
  • Add requirement-to-test traceability for Gates 2 and 3.
  • Generate comparisons only from real run artifacts.
✓
The base project is credible because it states its limits

The current project does not pretend Gates 2 and 3 are complete. Its one live Gate 1 comparison is labeled n=1. That distinction—implemented versus designed, mechanism evidence versus a measured rate—is exactly what the Zura16 branch erases.
